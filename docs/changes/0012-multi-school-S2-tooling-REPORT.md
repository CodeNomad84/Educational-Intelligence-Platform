# CHANGE REPORT — Multi-school hosting, stage S2: membership backfill and lifecycle tooling, student-school backfill, gate checks
Proposal: `0010-multi-school-hosting-PROPOSAL.md` §9 (S2), D-MS-9 (option B) · ADR-0012 · Level: L3 · Date: 2026-10-19 · Commits (local, **not pushed**): `6df2098`, `3a8fe9b`, `f706a32`, `46b1c1e`, `0fbc914`, `9f3a440`, `561ffae`, `350aecd` (code; the last four follow the owner's S2 review decisions of 2026-10-19/20) and the docs commits that carry this report (`47eab83`, `e1fa989`, and the one after `350aecd`) · Status: **implemented locally, pending owner review**. S2b and later, 2.2-0, 2.2 and 2.4 are NOT started.
Rule that still applies: NO REAL STUDENT DATA until the P3 exit criteria and the 2.4 audit log. Everything below ran on synthetic data or empty databases, and (for the tools) with exactly one School.

## WHY
Before S3 can switch the SchoolAdmin read scope to memberships, the data must be ready: every SchoolAdmin needs a membership, every student a school, orphan memberships must be visible and removable (S1 review findings F2, F4, G3, H2), and the operator needs a gate that says "READY" only when S3 would hide nothing. S2 delivers those tools **without changing any access**.

## WHAT
1. **G3 (commit `6df2098`):** an existing inactive membership row is no longer re-validated; on an existing row `clean()` reports a non-field error; the `user` of an existing row is read-only in the admin. A dual-role, superuser, inactive or outside-group row can therefore be **deactivated** in the admin (before: "invalid choice", delete only).
2. **Membership tooling (`3a8fe9b`):**
   - `backfill_school_memberships`: dry-run by default; with **exactly one** School every active, non-superuser `SchoolAdmin` who is not in `PlatformAdmin` and has no row gets a membership; zero or several Schools: nothing is guessed, the eligible user ids are printed and `--apply` is refused. Existing rows (also inactive ones) are never touched.
   - `check_school_memberships`: orphan report (reasons: inactive account, superuser, outside `SchoolAdmin`, also `PlatformAdmin`), exits 1 while active orphans exist; `--deactivate` (dry-run by default; `--apply` needs a new `--batch-file`) only sets `is_active=False`, never deletes; `--revert-batch` re-activates exactly the batch rows still inactive.
   - `schools/batch_log.py`: exclusive-create (`O_EXCL`, mode 0600) JSON batch files, ids only; `schools/membership_audit.py`: the classification.
   - **Runbook (D-MS-9, option B):** when a user is promoted to `PlatformAdmin`, deactivate that user's school memberships first or immediately after (`check_school_memberships --deactivate --apply --batch-file NEW`). The readiness gate blocks S3 while any exist.
3. **`backfill_student_school` (`f706a32`):** only `Student.school IS NULL` rows; class school, else the only School when exactly one exists, else unresolved (several Schools: nothing guessed); dry-run by default; `--apply` needs a new batch file and is **refused when a target student already holds a current enrollment** (staff scope would widen) unless `--accept-visibility-change`; `--revert-batch` sets NULL again only where the school still holds the written value and the student has no class. A student that already has a school is never changed.
4. **Gate checks (`46b1c1e`):** `check_access_switch_ready --multi-school` adds BLOCKERS `school_admins_without_membership`, `students_without_school`, `school_inconsistent_rows` (student/class school, enrollment/year school, grade or attendance linked to another student's enrollment), `active_memberships_of_platform_admin_users`; WARNING `memberships_invalid`; info `schools_count`, `school_admins_per_school`, superusers count. `compare_access_parity --multi-school` compares what each SchoolAdmin sees today (everything) with the membership scope (students, grades, attendance rows) and exits 1 if any would lose rows.
5. **Gate hardening (`0fbc914`, owner decisions 1, 2, 3):** the flag stays opt-in; without it both commands print `multi-school checks: NOT RUN` (JSON key `multi_school_checks`), with it `RUN`; the S3 gate requires BOTH commands with the flag (documented in the command docstrings, `CHANGE_GUIDE.md` and 0010 §9 S3, pinned by tests). New blockers in both commands: **D1** `no_school_admin_while_students_exist` (students exist but no active non-superuser SchoolAdmin account exists: no vacuous pass) and **D3** `memberships_invalid > 0` (a dormant grant blocks; it was a warning).
6. **Revert-tool hardening (`9f3a440`, owner decision 4), batch format v2:** the batch records only the rows ACTUALLY updated (rows are locked and re-selected inside the transaction, the update count is verified, the file is written before commit and removed if the write fails); membership batches record `user_id` and `school_id` per row and the reverts verify them; one shared id validator (`batch_log.valid_id`: real integer, 1..2**63-1, no bool/float/string/None) is used by every revert; invalid flag combinations are errors (`--apply` without `--deactivate`, `--batch-file` or `--accept-visibility-change` without `--apply`, `--revert-batch` together with any write option); the path is checked before any database work; the membership backfill refuses if the database returns no ids.
7. **E1 (`561ffae`):** blocker `schools_with_students_but_no_school_admin` in both `--multi-school` commands: a school that has students and is covered by no valid SchoolAdmin (an ACTIVE membership of a user who still qualifies, per `school_ids_for_admin`) blocks the gate, so "some admin exists" is no longer enough.
8. **Follow-ups (`350aecd`):** a GIVEN `--revert-batch`/`--batch-file` with an empty, whitespace-only or NUL-containing value is an error (never a dry-run); `Unsupported batch version N` is a message of its own (a non-integer version is never echoed); `write_batch` converts NUL/invalid paths to a `CommandError`, cleans up on `BaseException` (also `KeyboardInterrupt`, `MemoryError`) and unlinks only a file that still has the (device, inode) it created; every row lock is `select_for_update(of=('self',))` with `order_by('pk')`; both gate commands emit the boolean `multi_school_checks_run` in JSON (false without the flag, true with it, present also when the command fails); the documented S3 gate relies on it.
9. **No migration; no change to `visible_*`, views, serializers, permission classes or the token.**

## HOW
Evidence-only tools in the style of `backfill_enrollments`: dry-run default, counts only, a batch file that is written inside the transaction before it commits, queryset updates restricted to the expected prior state, state-checked reverts. The gate flag `--multi-school` is **additive**: without it both commands print exactly what they printed before (verified byte-for-byte, below).

**Gate flag (owner decision 2026-10-19):** the `--multi-school` checks stay opt-in so that the default invocation keeps its 4c meaning; to stop a default READY being misread, both commands now say `multi-school checks: NOT RUN`. S3's gate is `check_access_switch_ready --multi-school` plus `compare_access_parity --multi-school`, both required. Verified on the synthetic scratch database: the default outputs differ from the pre-S1 baseline by exactly that one added line (`diff` shows `multi-school checks: NOT RUN` and nothing else).

## RISKS
- The tools write (backfills, deactivate, reverts) when `--apply` is given; they only run against a database the operator names, with a new batch file, after a dry-run; nothing runs automatically.
- `backfill_student_school` assigns the only School to class-less students (one-time population, not a runtime default; creation paths are S2b). It will refuse when that would widen staff visibility.
- Limits of the tools: "users who left `PlatformAdmin`" cannot be detected (no history); the runbook step is the control, and the gate catches current dual-role state only. A re-activated batch row of an orphan stays an orphan (warning printed).
- The remaining items of the security review below.

**PostgreSQL lock observation (S2 review R8; PostgreSQL 16.14, disposable container, one membership row and one student; SQL taken from the ORM compiler, locks read from `pg_locks` for the transaction's own backend):**
| Query | SQL shape | Tables row-locked (`RowShareLock`) |
|---|---|---|
| OLD membership `select_for_update()` + default ordering | `… FROM schools_schoolmembership INNER JOIN schools_school … ORDER BY schools_school.name, user_id … FOR UPDATE` | **`schools_school` and `schools_schoolmembership`** |
| NEW membership `select_for_update(of=('self',))` + `order_by('pk')` | `… FROM schools_schoolmembership … ORDER BY id … FOR UPDATE OF "schools_schoolmembership"` | `schools_schoolmembership` only |
| OLD / NEW single row (`.first()`) | same pair of shapes | `schools_school` + membership / membership only |
| OLD / NEW student | `ORDER BY grade, last_name, first_name FOR UPDATE` / `ORDER BY 1 FOR UPDATE OF "students_student"` | `students_student` in both (no join; only the order differs) |
So the old form did also row-lock the joined `schools_school` row because of `SchoolMembership.Meta.ordering`; the new form locks only the table being changed. SQLite ignores `select_for_update`, so there `of=` has no effect (checked by recording the calls and by the executed SQL: no join, primary-key order).
