# 0018 — Migration-order guard (2026-10-25)

**Problem.** `students.0009` always creates "Default School"; `schools.0010` gives every school that exists when it runs a `tutor_ai` module row. Nothing in the migration graph orders them. When a new migration's dependencies flipped the plan (found with `missions/0003`), a fresh database licensed a module for the default school and 54 tests failed in setUp.
**Why no explicit dependency.** `students.0009 -> schools.0010` (or `run_before`) was tried in a scratch worktree: a database with `students.0009` applied and `schools.0010` not (any database behind on migrations) fails `migrate` with `InconsistentMigrationHistory`. The fix would therefore break existing installs; editing the applied migrations is excluded by the rules.
**What was done.** A guard instead: `schools/test_fresh_migrate.py` migrates an in-memory SQLite database from zero in a fresh interpreter and asserts (a) no module rows exist for any school and (b) `schools.0010` precedes `students.0009` in the plan. Mutation: making `schools.0010` depend on `students.0009` fails it (`[['default','tutor_ai']] != []`). It runs in the SQLite and PostgreSQL suites and in CI. On PostgreSQL the test database itself is built by a from-zero migrate, but the module-row assertion is only made on SQLite.
**Not done / open.** The order is still protected, not enforced. Options if you want it enforced: a new migration that clears module rows of a lone, student-less default school (can delete a deliberate grant: not recommended) or a later squash. Rule for new migrations: depend only on the previous migration of their own app.
